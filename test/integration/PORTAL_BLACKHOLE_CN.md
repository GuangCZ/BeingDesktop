# Portal 双向静默黑洞实测

使用官方 **heart-portal v0.8.0 Windows x86_64** 和桌面端实际 `PortalService`，在本机回环中继前增加 TCP 流转发器。测试开始于 `2026-09-05T23:14:49.079Z`，结束于 `2026-09-05T23:16:43.383Z`，6 项检查均通过。

| --- | --- |
| 初始真实连接 | PID 107628 完成中继握手及 MCP `initialize` / `tools/list`。 |
| 双向静默时长 | 110,004.973 毫秒。 |
| Portal → 中继 | 丢弃 295 字节。 |
| 中继 → Portal | 丢弃 442 字节。 |

控制台在 90 秒整的进度采样仍显示 `connected`，随后约 11 毫秒才收到真实超时事件。状态变化由 Portal 日志驱动，桌面端没有使用前端计时器提前虚构断线。官方实现每 15 秒检查一次“超过 90 秒未收到帧”，本次耗时不代表所有环境都会精确在第 90 秒断开。

## 故障注入方式

```text
真实 Portal → 127.0.0.1 TCP 转发器 → 127.0.0.1 受控 WebSocket 中继
                   ↑ 双向丢弃字节 110 秒
```

先建立真实 WebSocket 和 MCP 通路，然后转发器继续接收双方数据但不向对端传递。中继每 5 秒发送无业务内容的 `keepalive_ack`，确保下行方向也有可计量的丢弃数据。转发器在启用故障时不关闭连接；Portal 根据自身的心跳机制发现静默并重新连接。

这验证的是 **应用/TCP 流层的双向静默**：操作系统内核仍处理 TCP ACK。没有使用防火墙制造 IP 包级黑洞，没有修改网卡或系统网络，没有执行系统睡眠。这些范围必须与实机睡眠恢复测试分开报告。

测试没有接触生产 Heart、生产 Being 或远端 `cz-win`，没有业务工具调用，也没有证明 Windows 强制退出能够优雅清理运行中的工具子进程。
